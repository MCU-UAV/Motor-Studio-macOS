| 广播停止写失败会直接返回，跳过已知 ID 的停止 | 仍逐台发 Stop；整体结果保留失败。模拟广播写失败验证所有 ID 都收到尝试 |

| 总线频率分摊后，单台周期可能达到一秒看门狗 | 实机启动要求 ID 数 / 总线 Hz < 0.5 s；这是本应用的余量，不是协议的新阈值。运行引擎验证 1 台/1 Hz、2 台/2 Hz、15 台/20 Hz 均拒绝 |

| RestartMotor 多发了 Boot command 4，依赖短暂 Boot 窗口 | 广播 Stop / 目标 reset 后轮询应用 Stop，不要求额外 Boot ACK；对照 SDK `2319ea290` 的应用轮询逻辑 |
| 维护后的 Stop 回包带 error/timedOut 仍报告成功 | 维护 Stop 回读要求模式、ID、error、timeout 均正常 |
| 限位行程极小非零，量化成零会选择高精度模式 | 量化后行程为零直接拒绝；正负极小值回归 |
| 改 ID / 波特率在设备已生效后失败，界面仍当旧连接正常 | 状态修改操作失败或取消关闭会话；界面读取实际主机速率，显示断开并清旧状态。模拟 ID 已变化但 ACK 丢失，以及主机已切速后最终反馈失败 |

## 验证边界

48 项 MotorCore XCTest 通过；`scripts/test-startup-runtime.py` 编译并运行真实 AcquisitionEngine、记录模块和有锁存状态的模拟串口，验证完整同步/异步启动、故障及停止路径。SwiftUI / Observation 源文件通过语法解析。原生模型清草稿检查补进 `scripts/test-native-runtime.swift`，本次 Linux 无法运行该 Mac 测试；尚未重新验证 Mac 构建和 UI 行为。

500 ms 新鲜度检查不提供实时系统保证；OS 在实际串口写入附近暂停等边界仍要实机验证。协议无事务序号，同 ID 的 CRC 正确旧回包仍不能完全区分；已加强能区分的模式和私有命令回显，不能声称消除了所有延迟回包风险。

Boot 切换应答、真实碰撞、设备保存/重启时序、升级/标定持久化仍需要硬件验证。此前缺少的持续临时引导循环已在逐项验证后补入，含开始/退出、断线重连和串口独占；广播本身不提供设备状态确认。后续修复与 57 项回归结果见 VALIDATION.md 首节。
